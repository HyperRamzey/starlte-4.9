### boot.img

- Assembled with the **ROM's own host `mkbootimg`**, `/root/rom/crdroid16/out/host/linux-x86/bin/mkbootimg`.
  Every parameter was taken **verbatim** from `unpack_bootimg --format=mkbootimg` run against the
  shipping `out/target/product/a30s/boot.img` — no value was invented.
- Shipping `boot.img` header, as read: page size **2048**, header version **1**, `os_version`
  **16.0.0**, `os_patch_level` **2026-09**, cmdline `androidboot.hardware=exynos7904`, base `0x0`,
  `kernel_offset` `0x10008000`, `ramdisk_offset` `0x11000000`, `tags_offset` `0x10000100`,
  `second_offset` `0x0`, boot header size **1648**.
- **The shipping `boot.img` contains only kernel + ramdisk** (kernel 31,710,944 B, ramdisk
  1,649,333 B). **There is no device tree inside it.** Do not go looking for one.
- Ours **reuses the shipping ramdisk unchanged** (md5 `6c6af99689bcf805084025313de497d8`) and packs
  our own `Image`. Nothing about the rootfs is touched.
- Verification was not eyeballed: our `boot.img` was unpacked and compared against the shipping
  header **field by field** — every field identical except `kernel_size` — and **both payloads
  round-trip md5-identical** after a re-pack. The `ANDROID!` magic is intact.
- Fits the 33,363,968 B `boot` partition with **8,103,936 B headroom**.

**Trap — load-address arguments.** The Samsung `mkbootimg` in this ROM takes load addresses as
`--kernel_offset` / `--ramdisk_offset` / `--tags_offset` / `--second_offset` / `--base`.
**`--kernel_load_addr` and `--ramdisk_load_addr` are rejected** with `ValueError: Unrecognized
arguments`. They are upstream AOSP spellings, and they fail here.

### Device tree packaging

**`dtbtool` reads `model_info-*` from `fdt_path_offset(dtb, "/")` — the ROOT node of every blob it
is fed.** Not from a subnode, not from the first entry: the root of each file.

- When the property is **absent**, `dtbtool` reports
  `model_info-chip of <file> is of invalid size, skipping` and then
  `unable to locate any dtbs in the given path`. **"Invalid size" means ABSENT, not malformed** —
  that reading cost real time. It is the message for a missing property.
- **All five blobs must carry the block — the base DTB included**, even though stock's base has
  none. `dtbtool` is fed the base too, so a base without `model_info-*` kills the whole run.
- Commit `b29ad447f74b` added to the base DTB **and all four overlays**:
  `model_info-chip = <7885>`, `model_info-platform = "android"`, `model_info-subtype = "samsung"`,
  plus `model_info-hw_rev` / `model_info-hw_rev_end` ranges that track each overlay's own
  `dtbo-hw_rev` — 00 → 0/0, 01 → 1/1, 02 → 2/2, 03 → 3/255. **Written by hand from the overlay
  hw_rev values. Not copied from jackpotlte.**
- Only `model_info-hw_rev` and `model_info-hw_rev_end` are actually **consumed by a driver**:
  `drivers/battery_v2/sec_battery_data.c:258,263`. `model_info-chip` and `model_info-platform` exist
  to satisfy `dtbtool` and nothing reads them.
- `dtb-hw_rev` / `dtb-hw_rev_end` have **zero reader drivers** in the 4.9 tree. The base node keeps
  them only to match stock.

**Format correction — the shipping container is `mkdtboimg`, not the kernel's `dtbtool`.** The
board ships DT in a Samsung `0xd7b7ab1e` table container built by `mkdtboimg` via
`device/samsung/exynos7885-common/build/tasks/dtbimage.mk`
(`mkdtboimg cfg_create $@ $DTB_CFG -d $DTB_DIR`). It does **not** ship the `DTBH` container that the
kernel's own `dtbtool` emits. So there are two `dtb.img` artefacts and they are not alternatives:

| variant | container | size | role |
|---|---|---|---|
| kernel `dtbtool` output | `DTBH` v2, 5 entries | 512,000 B | built and recorded, but **not** the shipping format |
| `mkdtboimg` repack | `0xd7b7ab1e` (magic `d7 b7 ab 1e`) | 92,160 B | **the shipping-format deliverable** |

For reference, the shipping 4.4 `dtb.img` is 88,064 B, md5 `de969cbeb0183bd579229c68aac00820`.
The 92,160 B vs 88,064 B difference is expected: our set is not byte-identical to stock's.

### Extraction recipes (do not re-derive)

- Samsung `dt.img`/`dtbo.img` are a `0xd7b7ab1e` table container, **big-endian on disk**. Walk the
  FDTs by each FDT's own big-endian `totalsize` — the inter-FDT stride is **not** uniform
  (observed 102,360 / 102,196 / 102,876 / 103,076), so any fixed stride desyncs.
- The IKCONFIG payload: `IKCFG_ST` sits in `.rodata` **outside** the gzip member (gzip starts +8),
  `IKCFG_END` is stripped in shipping, and `gzip.GzipFile` fails on the missing trailer. Use
  `zlib.decompressobj(31)` and score candidates by `CONFIG_` count.
- `xxd` is **not installed** in this WSL. Use `od`.
- Available: `lz4`, `simg2img`, `dtc`, `debugfs`, `e2fsck`, `resize2fs`. Absent: `unpkgimg`,
  `binwalk`.
- `mkbootimg` is **not on PATH and is not needed as a package** — take the ROM's own built host copy
  at `/root/rom/crdroid16/out/host/linux-x86/bin/mkbootimg`, with `unpack_bootimg` from the same
  output tree, to read and rewrite `boot.img`. That is exactly how our image was built (§1).
- The kernel's own `scripts/dtc/dtbtool` is a **different** tool with a **different** output format.
  It is not what makes the shipping image — see §1, "Device tree packaging".

### Architecture facts, all measured

- **SoC:** Exynos7885. `soc_id=EXYNOS7885`, DT compatible `samsung,exynos7885`. **`EXYNOS7904` is
  a machine/board label**, not a different die — zero `exynos7904` symbols in the kernel.
- **CPU:** 6× Cortex-A53 + 2× Cortex-A55, 8 cores. *(An early assumption of 4× A53 was wrong.)*
- **GPU:** Mali-G71 MP2, **Midgard r26p0** — confirmed from live SurfaceFlinger
  (`OpenGL ES 3.2 v1.r26p0-01eac0`) and stock DT `compatible = "arm,mali"`.
  `03_mainline_status.md` in the evidence corpus wrongly says G71 is Bifrost/panfrost — it is
  **Midgard → `lima`**.
- **USB:** **Type-C**, and the PD stack is real and kernel-resident. Three confirmations:
  `/sys/class/typec/port0` on the live device (the class is `typec`, **not** `usb_typec`);
  `CCIC_S2MU106=y` in stock; and the stock `bootargs` literally pass **`ccic_info=0x1`**.
- **WiFi/BT:** Samsung **SCSC** mx140, not Broadcom. `scsc_wifibt@120c0000`, firmware in
  `/vendor/etc/wifi` (`mx140.bin` + a `_t` twin). **`CONFIG_BT` is `not set` in both stock and our
  own crDroid 4.4** — SCSC provides the entire Bluetooth stack. Mainline `CONFIG_BT` is *wrong* here,
  not merely unnecessary.
- **Camera:** rear IMX576 (48 MP) + front GC5035 + HI1631 + 4HA modules, DW9808 OIS actuator, 3
  EEPROMs. FIMC-IS **v6.20**, MFC **V11**.
- **Power:** entirely S2MPS/S2MPU — `s2mpb03pmic`, `s2mpu08mfd`, `s2mu106mfd`, `s2mu106-charger`,
  `s2mu106-fuelgauge`. **No Qualcomm MAX77xxx node exists anywhere in the stock DT.**
- **Panel:** S6E8FC1, 1080×2340. DT reports 720×1560 for the timing block.

## 3. Build system

Neutron Clang 24 for the target, a separately pinned older clang for host tools, `-Werror` on.

```
CC=/root/toolchains/bin/clang
HOSTCC=<rom>/prebuilts/clang/host/linux-x86/clang-r563880c/bin/clang
HOSTCXX=<rom>/prebuilts/clang/host/linux-x86/clang-r563880c/bin/clang++
CLANG_TRIPLE=aarch64-linux-gnu-
CROSS_COMPILE=aarch64-linux-gnu-
STRIP=<rom>/prebuilts/clang/host/linux-x86/clang-r563880c/bin/llvm-strip
O=/root/port49/obj_a30s
```

Use **`make -k`** while the tree is dirty. It surfaces every error in one pass instead of stopping
at the first, which is how the 3,336-object figure and the full error inventory were obtained in
~54 s of wall time. For a final build, use the plain `all` target and read the real exit code.

**Always build the `all` target. Never build `Image`.** `arch/arm64/Makefile` recurses for
`Image: vmlinux` **with no dependency on `DTB_OBJS`**, so a bare `make Image` links the kernel and
stops — it can never produce a DTB. Only `all` runs the 11 DTC steps. A green `Image` is therefore
*not* evidence that the device tree built, and this is a mistake worth making exactly once. (Also
recorded in §8.)

**Never edit the defconfig while a build runs** — `streamline_config.pl` rewrites it.

   `include/exynos-fimc-is-sensor.h` is byte-identical across all four forks — so for a 7885-DDK

   SoC-specific; the forks are a *style/idiom* reference.
2. **They are useless for the S2MU106 stack.** Their `drivers/muic/` and `drivers/ccic/` are
   byte-identical to each other and contain only `s2mm003`/`s2mm005`/`max77705`/`max77854`/
   `max77865`/`sm5508`/`tsu6721` — zero overlap with S2MU106. Verified: 0 `s2mu106` files in all
   five clones.
3. **`eh_9810` (4.9.337) and `els_starlte` *regressed* the FIPS anchor fix** back to the bare
   `optimize("-O0")`. That is why the 4.9.219 tree is the right source there, not the newer one.
4. **There is no Exynos7885 4.9 tree anywhere.** All 16 GitHub 7885 repos are 4.4. No A30s
   defconfig, DT or `.config` exists in any surveyed tree. Do not go looking again.

  `MALI_SEC_VK_BOOST`/`MALI_DMA_BUF_LEGACY_COMPAT`/`MALI_MIDGARD_ENABLE_TRACE` → `n` to match stock.
- **VTS off** — stock has it off, so the 15 `vts.c` errors were caused by the config asking for a
  subsystem the device lacks. *Adding 7885 register arms would have been the wrong repair.*
- **Qualcomm family out entirely** — there is no Qualcomm PMIC node in the DT.
- **Mainline Bluetooth out** — `SCSC_BT` is the whole stack.
- **`SEC_DEBUG` and `SEC_DEBUG_PPMPU` deliberately KEPT `y`** even though stock lacks the latter:
  the 4.9 tree's `traps.c` needs `print_ppmpu_protection`, and the SEC debug tree carries callers
  that assume the SEC debug build. **These are decisions, not leftover drift** — see the correction
  in §8. Clearing them toward stock would be a regression.
- **`SEC_DEBUG=y` and `SEC_DEBUG_PPMPU=y` are not "non-stock" in the sense of "wrong".** The
  convergence target is the stock config where the stock config is evidence, and it is *not*
  evidence here. Where the 4.9 tree genuinely needs a symbol stock omits, keeping the symbol is the
  correct outcome and the divergence gets recorded here rather than silently closed.
- **`MUIC_HV_12V` stays `n` — deliberately, not converged away.** 12 V charging comes from Type-C
  PD (`MAX_CHARGING_VOLT 12000`), not MUIC AFC, whose S2MU106 path only ever produces 5 V and 9 V.
  This is a hardware fact, so there is nothing to converge toward.

### The §18.6 trap that cost 110k lines of invisible work
Applying the config and then checking the **resolved `.config`** revealed 15 symbols requested and
**silently dropped** — including *all* of SCSC and *all* of SENSORS, because the top-level
`drivers/misc/{Kconfig,Makefile}` and `drivers/net/wireless/{Kconfig,Makefile}` never referenced
them. **A defconfig line for a symbol kconfig never sees is a no-op that reads as success.**
Always verify against the resolved `.config`, not the defconfig.

**The link is done.** Compile errors zero, undefined references zero, every artefact produced. The

**Nothing below is a build problem any more.** Everything that remains is device validation, and

## 8. Corrections and self-inflicted errors (kept so they are not repeated)

- **`MALI_KUTF` was set to `n` "to match stock" while the decision table printed `stock=m` on the
  line above.** Corrected to `m`. Both a 4.9 r26p0 Kconfig default and a sibling defconfig say `m`.
  *Lesson: read the evidence your own tooling printed, before applying the change.*
- **The `MALI_TMIX` duplicate.** The 7885 block defined a second `MALI_TMIX`, but `tMIx/Kconfig`
  already defines it as a tristate for the Exynos8895. **kconfig parses every stanza regardless of
  the surrounding `if`**, so this was a duplicate symbol with a conflicting type and the type was
  picked arbitrarily. Resolved by using `MALI_MIDGARD` — the correct name, already declared by
  `b_r26p0/Kconfig`, and already `y` in stock.
- **`IRQF_PERF_CRITICAL` — the premise was inverted.** It was claimed "only compared, never passed
  to `request_irq`". True for the fingerprint drivers; **false** for `dpu_7885` and `b_r26p0`, where
  all 9 sites pass it directly, and the 4.4 donor's `kernel/irq/manage.c` genuinely implements it
  (files the desc on a `perf_crit_irqs` list for cpufreq/thermal migration). Substituted
  `IRQF_NOBALANCING` rather than deleting the bit.
- **`include/linux/sync_fence.h` does not exist in either tree.** 4.9 replaced
  `drivers/staging/android/sync.h` wholesale (`sync_fence`→`sync_file`, `sw_sync_timeline`→
  `sync_timeline`). The decisive reference was **our own already-ported `dpu_9810/`**, not the
  sibling forks and not the mali include that the brief cited.
- **`CONFIG_REGULATOR_S2MPS16` is a non-issue.** Absent from the *stock* config too, and the stock DT
  publishes no regulator node and no `clocks` property for `mali` — the 7885 GPU rail is fixed,
  driven by a direct cal-if/PMU write of `gpu_default_voltage` (800000 µV).
- **The `of_clk_get` "first-boot risk" was wrong.** `mali_kbase_core_linux.c:3920-3928` breaks on the
  first failed lookup, sets `nr_clocks = 0`, and never checks the `-ENOENT` — the comment above it
  says so explicitly. It does not demand ≥1 clock.
- **`BCM_GPS_SPI_DRIVER` is not legitimate here.** Stock builds no Broadcom GPS driver at all and
  uses `samsung,gnss_shdmem_if` (shmem+mailbox to the modem). The `bcm_setup=` bootargs string
  appears identically in the 9810 DTS — lineage boilerplate, not evidence.
- **`MFC` "V12" is a runtime version-detecting driver that already supports V11** — same DT
  compatible, register map a pure superset at identical offsets. It was silently carrying 9810
  addresses (`0x17880000`, 0 hits in the stock DT) that `ioremap()` would have turned into a
  writable alias of live DRAM.
- **`drivers/power/s2mu106_power_compat.h` aliased the shared extended-property window.** All 28
  of its values (86..113) collided with the canonical enum — e.g. `S2MU106 VCC1` *was*
  `AICL_CURRENT` — so the AICL current limit was being written to one value and read at another and
  silently dropped. Window moved to a private 342..367.
- **"Our overlays are missing the fingerprint `.dtsi` include" — FALSE.**
  `arch/arm64/boot/dts/exynos/dtbo/exynos7904-a30s_eur_open_00.dts:18` carries
  `#include "exynos7904-a30s_fingerprint_00.dtsi"`, byte-identical to the donor. *Lesson: assert
  the absence before reporting it, byte-compare when you do.*
- **"There is no haptic driver" — FALSE.** `drivers/misc/s2mu106_haptic.c` exists and is linked. It
  supplies `haptic_homekey_press`, `haptic_homekey_release`, `sec_haptic_register` and
  `sec_haptic_unregister` — the four symbols §1 had listed as unresolvable. *Lesson: a missing
  symbol is not evidence of a missing subsystem; grep the tree for the provider's filename first.*
- **"The stock DT omits all camera sensor nodes" — FALSE.** Per-sensor CIS / EEPROM / actuator nodes
  are present in the A30s overlays. The genuine gap is the **EEPROM calibration data**, and the tree
  is built against `VENDER_MCD` not `VENDER_MCD_V2`. The node-level claim and the calibration-level
  claim are different claims; only the second one survives.
- **`SEC_DEBUG=y`, `SEC_DEBUG_PPMPU=y` and `MUIC_HV_12V=n` are decisions, not drift.** They diverge
  from the stock config on purpose, each for a stated hardware or 4.9-tree reason (§6). A defconfig
  that does not match stock line-for-line is not automatically a defconfig with errors in it.
- **A green `Image` is not a green build.** `arch/arm64/Makefile` recurses for `Image: vmlinux` with
  no dependency on `DTB_OBJS`, so `make Image` can never produce a DTB. Build `all`. The DT steps
  are invisible in a per-file dependency graph — check the artefact count, not the exit code alone.

## 9. Lessons that generalise

- **Ground truth beats source reading.** The stock firmware dump answered in minutes what hours of
  reading 4.4 source could not: the overlay `model` strings, the exact sensor set, the real panel,
  the real config, and the fact that the PD stack is real.
- **A "select" overrides a "depends on".** `SND_SOC_SAMSUNG_DISPLAYPORT` was `y` in the resolved
  config while its own `depends on SOC_EXYNOS8895 || SOC_EXYNOS9810` was unmet, because a `select`
  from the 9810 machine forced it. **Only the Makefile gate was holding it**, and it is load-bearing
  — do not remove `sound/soc/samsung/Makefile`'s SoC check.
- **Silently-dropped symbols read as success.** Verify the *resolved* `.config`, every time.
- **`-k` is worth 10× the wall time** on a port this size.
- **Duplicate symbols across generations are the dominant hazard** of an in-tree multi-SoC port.
  Check collisions before enabling, not at link.
- **The kernels with a live build are the trustworthy ones.** The A30s DTS is byte-identical to the
  4.4 donor *and* corroborated node-for-node by the real stock DTBs — that is why display needed
  no DTS work at all.
- **"Invalid size" usually means "absent".** `dtbtool`'s
  `model_info-chip of <file> is of invalid size, skipping` fires when the property is *missing* from
  the root node, not when it is malformed — and it is per-blob, so one bare base DTB kills a run
  that fed it four perfectly good overlays. Read the error as "which blob, and which node?", then
  check what the tool is actually asking for.
- **A tool that builds the artefact is not the tool that ships it.** The kernel's `dtbtool` emits a
  `DTBH` container; this board ships a Samsung `0xd7b7ab1e` container built by `mkdtboimg` from
  `device/samsung/exynos7885-common/build/tasks/dtbimage.mk`. Both were built, and only one of them
  is the shipping format. **Always identify the deliverable's format from the device, not from the
  kernel tree** — the tree's tools are for the tree, not for the product.
- **A clean link proves the code is self-consistent, not that the hardware will run.** The single
  biggest lesson of this port. Every wrong-SoC caller can be guarded to the point where the linker
  is perfectly happy and the device is still wrong. §11 exists because this is easy to forget
  after a green build.

## 11. What is and is not proven about the hardware

A green build is a compiler result. This section exists so the two are never confused.

### PROVEN

- **The tree compiles and links clean.** `make all`, `rc=0`, 0 compile errors, 0 undefined
  references, 3,613 objects, 11 DTC steps, 3 expected `ld.bfd` RWX LOAD-segment warnings.
- **Every artefact is produced and md5-recorded:** `Image`, `vmlinux`, the base DTB, all four DTBO
  overlays, both `dtb.img` variants, `boot.img`, and the single module `kutf.ko` (§1).
- **The `boot.img` header is field-identical to the shipping image** except `kernel_size`, and
  **both payloads round-trip bit-exact**. The `ANDROID!` magic is intact and the shipping ramdisk
  is reused unchanged.
- **Subsystem object counts prove the stack is real, not stubbed:** F2FS (257 symbols / 21 objects),
  ZRAM (29), m2m1shot2 (48), GDC (16), Mali/kbase (~1,200), and SCSC + S2MU106 all linked.
- **The sensor set is present:** IMX576, GC5035, HI1631, 4HA, and the DW9808 OIS actuator.
- **The USBDRD3 probe is correct.**
- **30 MIPI-PHY symbols are resolved**, so the display/camera PHY layer is linked rather than
  stubbed.

### NOT PROVEN

- **Nothing from this port has ever been booted.** No 4.9 kernel has been flashed. There is no boot
  log, no dmesg, no init reachability, no `pidof vectord`, no gate-battery pass. Every claim above
  stops at the artefact.
- **The device is a production phone running the 4.4 build #75.** It is the user's daily driver and
  its data is real.
- **Touch cannot work.** The **Imagis IST40xx touchscreen source is ABSENT from the tree**, despite
  a valid DT node. The ET7XX fingerprint stack that *is* ported is a different sensor. A valid node
  and a missing driver look identical from the DT — and only one of them probes.
- **Camera images would be uncalibrated.** The build uses `VENDER_MCD`, not `VENDER_MCD_V2`, and the
  **A30s EEPROM calibration data is absent**. IMX576, GC5035, HI1631, 4HA and DW9808 all being
  present is necessary, not sufficient.
- **TEEGRIS is disabled**, pending a recovered `startup.tazar`. It is wired, not enabled.
- **Highest delivery risk: the board ships an AVB-keyed prebuilt `dtbo.img` on p18.** A self-built
  unsigned `dtbo` may simply be refused by the bootloader. This is the one item most likely to
  turn a green build into a failed first flash, and it cannot be resolved from the host side.
- **`model_info-hw_rev` needs first-boot validation.** Those properties reach **four drivers** that
  previously took fallback values. Writing a real hw_rev where a driver used to see nothing is a
  behaviour change, not a no-op, and it has never been exercised on hardware.

### Standing rules

- **Do not flash anything from this port yet.**
- **`/data` must never be written.** Not for a test, not for a log, not once.
- Treat §1 as a build report and this section as the truth about hardware. When they disagree,
  **this section wins.**
